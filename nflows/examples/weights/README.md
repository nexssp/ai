# NFlow weight-editing examples

Seven illustrative flows: one practical weekly support-ticket triage calibration candidate, five small toys (`toy_*`), and one local llama.cpp baseline/candidate comparison. The practical flow uses only caller-supplied validation evidence (never holdout), caller-known tensor coordinate/current value and predeclared bounded deltas. A typed choice can hold or select one of those deltas; patching uses the exact inspect SHA-256, `expected_value` guard and a versioned copy path. It is a human-reviewed candidate—not deployment, a gain claim, or unattended calibration.

The toys demonstrate scalar SafeTensors editing, a pair-style scenario, a sharded SafeTensors index, a GGUF float tensor, and hold/stale-value guarding. They do not choose a provider or model. Before running a decision, set `LLM_DECISION_PROVIDER` to a driver supported by `ai.decide` and `LLM_DECISION_MODEL`; for `openai-compatible`, also set `LLM_DECISION_BASE_URL`. Supply credentials with `LLM_API_KEY`, or set `LLM_DECISION_API_KEY_ENV` to the name of an environment variable that contains the key. Supply matching real checkpoint metadata and paths only when executing; lint does not need checkpoints or provider credentials.

The `llama_cpp_compare.nflow` example is the exception to the no-inference statement: it runs an already-installed `llama-cli` through Flow's native `external.exec` and returns raw outputs for manual review. It does not download binaries/models, assign a quality score, or automatically improve a model. Other flows only inspect/patch files; weight patching does not establish model compatibility or quality. All examples are illustrative and none deploys a model.
